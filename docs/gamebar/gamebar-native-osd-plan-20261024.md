# 脱离 RTSS 的游戏识别与 Game Bar OSD 实施步骤

最新模板、Game Bar 关闭重开修复及安装版本见[当前实施记录](osd-template-and-gamebar-lifecycle-20261025.md)。
2026-10-25 后续需求已变更：性能显示单击循环 0—4 档、固定位置显示，不再由游戏识别控制可见性。当前实现见[固定性能显示实施记录](../performance/fixed-performance-osd-20261025.md)，下文仅保留原计划。

日期：2026-10-25。状态：保留旧 Game Bar 控制界面，已在原性能显示磁贴中加入新 OSD 选项，安装版本 0.4.34.0。实际验证结果、PresentMon 兼容回退和未验证场景见 [实施记录](gamebar-native-osd-implementation-20261024.md)。下文保留原实施顺序供核对。

目标：自动找到当前游戏，独立采集性能数据，并在现有 Game Bar 工具箱中切换 OSD 开关和 1—4 档。新安装、从文件夹直接启动的游戏也能进入自动识别流程，不要求逐款配置白名单。

## 1. 总体分工

| 部分 | 负责的事情 | 实现方向 |
| --- | --- | --- |
| 游戏会话 | 当前监控哪个游戏、何时切换、何时结束 | Game Bar 目标信息 + 游戏库启动关系 + 前台窗口与呈现行为 |
| 性能采集 | FPS、帧时间、CPU/GPU、温度、功耗、电池、风扇 | 复用 PresentMon 与工具箱已有硬件读数 |
| OSD 显示 | 在游戏上方画性能条和曲线 | 新增一个可固定的 Game Bar 监控组件 |
| 操作入口 | 开关、档位、大小、排版 | 复用现有 Game Bar 控制面板 |

数据方向：游戏会话选定目标进程 → 后台采集并发布统一数据 → 控制面板和监控组件共同读取。

控制面板负责调节；监控组件负责常驻显示。用户首次固定监控组件后，收起 Game Bar 仍可保留监控条。固定状态由用户和 Game Bar 管理，不能把程序自动固定作为既定能力。

## 2. 现有基础与缺口

- `native/ClawPower.cs` 的 `FrameStats` 已通过 `PresentMonAPI2.dll` 跟踪指定 PID，提供 `appFps`、`presentedFps`、`displayedFps`、帧时间等数据。当前依赖本机安装的 Intel PresentMon 共享服务。
- `plugin/claw_power.py` 已有硬件采样、OSD 设置和 Game Bar 数据接口，但 `_osd_tick()` 将采集、RTSS 配置、RTSS 文本绘制放在一起，需要拆开。
- 当前 `foreground_game()` 主要取前台进程并排除已知非游戏程序，尚不足以作为完整的游戏识别。
- AutoTDP 已有打开控制中心时继续跟踪原进程的局部逻辑；应整合进统一会话，避免监控、首页和功耗控制各自选择不同目标。
- `native/GameBarWidget` 已有控制面板及与后台的连接，可以扩展为同一安装包内的两个组件。

## 3. 第一步：验证 Game Bar 的识别和显示能力

先做一个最小验证页，确认设备上实际安装的 Game Bar、项目 SDK 和运行时支持情况。

1. 接入 `XboxGameBarAppTargetTracker`，监听 `TargetChanged` 和 `SettingChanged`。
2. 显示并记录目标名称、`IsGame`、`IsFullscreen` 和可用的窗口标识。检查本项目 SDK 是否暴露 `Hwnd`；支持时交由桌面后台解析 PID，不支持时使用后台窗口跟踪关联。
3. 检查目标跟踪是否已开启；未开启时展示一次明确的设置引导。拒绝或不可用时仍允许后台使用其他识别信号。
4. 分别验证游戏中、打开 Game Bar、关闭 Game Bar、切回桌面时返回的目标，不预设打开面板后接口必然保留原目标。
5. 新增最简单的监控组件，先只显示静态文字，实测固定、收起面板、透明背景、鼠标穿透和手柄操作。

验收：能够说明哪些目标信息实际可用，且固定后的监控文字能在代表性游戏中显示。真正独占全屏、紧凑模式、不同缩放比例需分别确认。

## 4. 第二步：建立统一游戏会话

建议新增 `plugin/claw_game_session.py`，由后台统一维护目标，并将 Game Bar 的目标变化作为一种输入。

识别依据按可靠程度组合使用：

| 信号 | 用法 | 边界 |
| --- | --- | --- |
| 用户曾明确纠正 | 记住“视为游戏”或“忽略此程序” | 属于少量例外配置，不承担所有游戏的识别 |
| Game Bar 的 `IsGame` | 作为系统提供的强信号 | 可能包含用户手动标记；不能认为覆盖全部游戏 |
| 从游戏库启动 | 关联库内记录与实际运行程序 | 启动器、Steam 转交启动时不能只依赖直接父子进程 |
| 前台窗口和实际呈现 | 为外部启动、系统未识别的程序建立候选 | 出帧本身不能证明是游戏 |

实施要点：

1. 从前台窗口和启动事件产生候选，再通过 PresentMon 确认候选的呈现活动；不需要持续对所有系统进程进行完整性能采样。
2. 游戏库启动关联综合路径、启动时间、窗口归属和进程关系，跟随到实际游戏程序，避免把启动器、更新器或崩溃报告器选为目标。
3. 窗口大小、全屏和渲染行为用于辅助判断，不以“必须全屏”“必须超过 30 FPS”作为门槛，照顾窗口化和低帧率 Galgame。
4. 对低置信候选保留“待确认”状态；不能因为存在交换链就自动认定为游戏。浏览器、播放器、工具箱界面需要防误识别。
5. 用 PID 加进程创建时间标识会话，防止进程退出后 PID 被复用。
6. 打开 Game Bar 时保留原游戏会话；切到桌面或其他应用时区分“后台运行”和“已退出”。前者可隐藏 OSD，后者才结束会话。
7. 没有帧率样本时保留游戏身份，单独报告采集不可用；加载、暂停或低更新频率不能直接判定游戏退出。

验收：监控、Game Bar 首页与 AutoTDP 使用同一个有效目标；打开面板不会把目标切成面板本身，切换两个游戏时不会串用旧数据。

## 5. 第三步：把数据采集从 RTSS 绘制中拆出来

1. 将 `_osd_tick()` 中的帧率和硬件读取拆成独立采集逻辑；RTSS 字体、缩放、共享内存和文本格式保留在旧绘制路径中。
2. 后台发布结构化监控快照，至少包括会话标识、PID、游戏名称、采样时间、数据来源、有效状态及各项数值。新组件不解析 RTSS 的文本标签。
3. 监控、首页和 AutoTDP 共享同一份采样结果，避免重复查询。根据实际消费者决定采样频率；关闭 OSD 后，AutoTDP 所需采样仍正常运行。
4. 切换会话时立即清空旧会话读数。服务断连、采样超时或数据过期时显示 `--` 和状态，不继续显示旧帧率。
5. 分开标注游戏渲染帧率与插帧后的帧率；沿用 AutoTDP 对真实渲染帧率的需求。某项数据无法获得时留空，不估造数值。
6. 用有效的逐帧时间序列绘制帧时间曲线；不能拿每秒平均 FPS 反推逐帧曲线。第一版可以先交付数值监控，曲线后续补上。
7. 明确 PresentMon 的交付方式：本机验证先复用已装服务；产品安装需检测兼容版本，并决定随包提供或引导安装。不能假定每台机器装了 Intel 显卡驱动就一定有该服务。

验收：停止 RTSS 后，后台仍能提供当前游戏的 FPS 和硬件读数；PresentMon 不可用时能明确降级，硬件监控按可用数据继续显示。

## 6. 第四步：新增 Game Bar 性能监控组件

1. 在 `Package.appxmanifest` 新增独立组件标识，在 `App.cpp` 按组件标识打开控制面板或监控页。
2. 监控页连接现有后台，订阅会话、监控快照和 OSD 设置。
3. 先实现一行和两行布局、大小档位，以及 1—4 档内容。新增 `OsdPage` 等显示文件，避免把监控界面继续塞进控制面板页面。
4. 根据窄窗口、高 DPI、横竖屏和字体大小调整排版，避免当前长监控条在小窗口中被截断。
5. 跟随 Game Bar 的可见性、透明度及用户穿透设置；无有效游戏、后台断连时显示清楚的状态，按设置隐藏监控内容。
6. 加入首次固定引导。用户取消固定或关闭组件后，控制面板要能区分“设置已开启”和“监控组件当前未显示”。

验收：固定组件并收起控制面板后，游戏中仍显示监控；显示区域不干扰正常游戏输入。

## 7. 第五步：接通现有 OSD 操作入口

1. 保留现有“关／1／2／3／4”操作方式，修改设置后由后台广播给监控组件。
2. 开启时由控制面板激活或恢复本包的监控组件；关闭时停止其监控显示。组件固定仍遵循用户设置。
3. 设置同时供 Game Bar、游戏库控制中心和 Steam 入口使用，避免三个入口各保存一份状态。
4. 过渡期间保留原 RTSS 绘制路径作为可回退方案，确保同一时刻只有一个 OSD 绘制路径开启，避免双重叠加。
5. 明确此次迁移的范围是游戏识别、性能采集和显示。现有限帧仍有单独的 RTSS 路径；若目标进一步变为彻底不安装 RTSS，还需另做限帧替代，不能宣称本次迁移已覆盖。

验收：所有入口操作同一份设置，重启后保留档位；关闭 OSD 不影响 AutoTDP、风扇等已有功能。

## 8. 第六步：实机验证并决定默认方案

| 场景 | 重点检查 |
| --- | --- |
| Steam 游戏、非 Steam 本地游戏、文件夹直接启动 | 无预先添加名单也能进入自动识别流程 |
| 启动器转交到实际游戏程序 | 目标跟随正确，不监控启动器 |
| 已知 Galgame、低帧率与静态标题画面 | 游戏身份不因少出帧而丢失；帧率不可采集时如实提示 |
| D3D9、D3D11、D3D12、OpenGL、Vulkan | 分别记录识别、帧率采集和叠加显示结果 |
| 窗口、无边框、真正独占全屏 | 分别确认显示效果，不以一种模式代表其他模式 |
| 打开和关闭 Game Bar、Alt+Tab、游戏最小化 | 保持会话，正确隐藏或恢复 OSD，不显示旧读数 |
| 浏览器、播放器、工具箱和多个游戏同时运行 | 防误识别，前台游戏选择正确 |
| XeSS 或其他插帧，以及 Magpie／小黄鸭运行时 | 不误选辅助窗口，渲染帧率和显示帧率来源清楚 |
| 反作弊游戏、PresentMon 服务中断、后台重启 | 记录兼容性边界，不绕过限制；异常能恢复 |

在同一游戏场景下比较关闭监控与开启监控时的 CPU 占用、内存、帧时间和整机功耗，检查掌机上的常驻成本。只有真实数据支持后才确定默认刷新频率和是否默认使用新方案。

建议开发顺序：最小能力验证 → 统一游戏会话 → 独立采集 → 数值监控组件 → 全部入口联动 → 兼容性与开销验证 → 曲线等增强功能。

第一版完成标准：在已验证的游戏与显示模式下，停止 RTSS 后仍能自动选定游戏、显示有效性能读数，并通过现有 Game Bar 控制面板切换 OSD；未覆盖场景明确记录。
