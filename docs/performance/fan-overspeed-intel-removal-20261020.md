# 删除 Intel 智能与风扇超转排查

用户报告：鸣潮、均衡档、CPU 约 75–80°C，风扇达到约 5800 RPM；手动 TDP 正常，要求删除 Intel 智能功耗选项。

## 已安装

- 后台 0.17.25；游戏库 0.1.20.0；Game Bar 小组件 0.4.19.0；独立风扇服务 1.0.1。
- 游戏库、Steam 工具箱、小组件的 Intel 智能入口及快捷轮换已移除，只保留 AutoTDP、按电源、手动。旧客户端或配置提交 `mode=smart` 时迁移到 AutoTDP，不再启用 Intel 自动策略。
- 保留旧 Intel 会话恢复代码及 AutoTDP 排他交接所需的驱动关闭接口，不卸载 Intel 显卡驱动或其他系统组件。
- 原 TDP、频率、AutoTDP 目标与上下限、三档风扇曲线均保留。测试前实际保存的是静音档，测试后恢复该选择；这不能反推用户出现问题时选择了哪个档位。静音与均衡都限制在 76% 曲线风量。

## 实机证据与结论

1. 读取时风扇服务运行、没有暂停、自定义控制位开启、全速位关闭。没有超转当时的历史采样，因此不能直接确定那次 5800 RPM 的原因。
2. 通过服务临时把当前档六个点设为 76%，采样 32 秒；两扇从约 2800 RPM 平稳升到 4660–4706 RPM，温度没有超过测试终止阈值。测试结束通过服务恢复原曲线。见 `diagnostics/fan-service/overspeed-calibration.json`。
3. 该结果说明在测试条件下，76% 本身不会让风扇稳定到 5800 RPM；按均衡曲线、75–80°C 也不会主动要求全速。仍需区分外部改写、EC 自身保护和错误回退，不能从占空比上限推断硬性的 RPM 上限。
4. 确认旧服务有一条可导致高转的路径：任何硬件读取错误都会立即恢复原厂 Auto，下一轮恢复后又清除错误。界面仍保留用户所选的均衡/静音档，原厂曲线却可能在该短暂期间提高转速。此路径已通过模拟故障验证；它是候选原因，尚不能证明用户当次就是此原因。
5. 风扇数据包的保留区没有改动。[ClawConfigurator 底层实现](https://github.com/Stev3FrencH/ClawConfigurator/blob/master/src/Hardware/Windows/WmiFanProvider.cs) 将第 8 字节标为 EC ceiling，不应把当前回读的 94 当成六点曲线并任意覆盖。本次也未修改它。

## 修正

- WMI 只读请求、CPU 温度读取最多重试两次，每次间隔 25 ms；短暂读取异常不再立刻退出自定义控制。写操作不自动重试，保留原事务及回滚。
- 持续传感器/写入失败仍交回原厂自动散热；保留温度保护、全速功能与非零风量校验。
- 配置/控制位被覆盖时仍重新写入，并记录 `external_control_changed`；静音/均衡关闭全速却读到超过 5000 RPM 时记录 `rpm_above_profile_expectation`；恢复原厂保护时记录 `factory_auto_fallback`。
- 每两秒保存当前 CPU/EC 温度、两个风扇 RPM、目标风量、实际表、控制位、档位、错误和恢复次数。日志在 `C:\ProgramData\ClawToolbox\FanService\telemetry.jsonl`，4 MiB 轮换并保留一份上一卷。仅本地记录，日志错误不影响散热。

## 验证

- 服务调速、事务、传感器故障、外部覆盖修复、超转诊断及原厂保护测试通过。新增测试确认一次温度读失败不再触发 Auto、持续失败仍安全回退。
- AutoTDP 18 项、旧会话/迁移 14 项、Python 风扇 25 项、功耗后端及前端测试通过。
- 已检查新版性能页，模式仅显示 Auto、按电源、手动。三个安装包版本及服务版本已确认，当前风扇与功耗接口没有错误。
- 实际鸣潮持续游戏、均衡档出现 5800 RPM 的场景尚待复测。不能把短时定风量校准或模拟故障通过当作该游戏问题已完全解决。

采样前后状态：`diagnostics/fan-service/overspeed-before.json`、`overspeed-after.json`。服务安装保留原厂备份，未刷 BIOS/EC 或修改安全设置。

## 再次复现后的定位与 1.0.2 修正

用户反馈仍到 5800 RPM 后，读取了新日志。这次有完整证据，前文的读取失败候选路径不是本次原因：

- 2026-10-20 05:48:19（本地时间），CPU 短暂到 85°C、EC 84°C，实际两路输出变成 94%，用户表仍全部为 64%。之后 CPU 降至 76–81°C，但实际输出继续保持 94%。
- 05:48:38 起两扇达到 5783–5854 RPM。整个过程 `software=true`、`fullSpeed=false`，读取重试、温度重试、覆盖修复计数均为零，也没有原厂 Auto 回退事件。
- 因而可排除本次是读取失败/退出服务所致。85°C 附近实际输出跳到保留的 94% 档，且与既有固件默认温度/风量表相符，支持 EC 高温增压这一判断。75–80°C 是增压后的读数，不能排除之前的短暂温度峰值。
- 旧服务仅核对六点表及控制位；这些始终正确，实际输出升到 94% 也不会触发恢复。只有目标风量后来改变、再次写表时，实际输出才下降，造成已经冷却却持续高转的现象。
- 本轮日志实际选择为静音；已通过现有配置接口切到用户要求的均衡，服务配置与工具箱缓存均为均衡，功耗各字段完全保留。

已安装后台 0.17.26、游戏库 0.1.21.0、风扇服务 1.0.2：

1. 75°C 起立即按用户曲线提高风量，不再等六秒；下降仍保留防抖。避免风量爬升落后于温升。
2. 检测静音/均衡实际输出超过 76% 的增压状态，不再仅依赖六点表判断。
3. CPU 和 EC 都连续十秒不高于 80°C 后，重新应用当前曲线；温度仍高、任一温度缺失或手动全速时不执行此恢复。恢复写入有十五秒间隔限制，不会密集争抢控制。
4. 不改 EC 的 85°C 阈值、94% 保留档或固件保护逻辑。若温度重新达到 EC 保护条件，仍允许其提高转速。界面增加“EC 高温保护 · 冷却后恢复曲线”，并把原“转速上限”改为“曲线预期”，避免把预计转速当成硬限制。

新增模拟回归通过：80°C 立即升风量；CPU/EC 仍热不重写；仅 CPU 冷却不恢复；双温度稳定满十秒后，表未变但实际输出 94% 的情况也能恢复；正常输出不额外写入。功耗与 Python 风扇测试通过。

证据：`diagnostics/fan-service/thermal-boost-episode.json`（完整温升/超转/下降过程）、`overspeed-events.json`、`thermal-recovery-live.json`。前一节“尚未复现”的结论仅适用于 1.0.1 安装时的短测，已被本节实机日志更新。

1.0.2 安装后的实机采样也捕获到恢复：实际输出 94%、目标 71%，CPU 74–78°C；`thermalRecoveryCount` 从 1 增为 2 后，实际输出回到 71%，随后 RPM 从 5854 逐步降到 3664–3902，控制位正常且没有错误。原厂 94% 保留字段仍不变。该结果验证冷却后恢复已实际执行，不代表将 EC 的高温保护强行限制在 4700 RPM。
