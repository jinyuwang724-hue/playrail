# 智能功耗实现排查 · 2026-10-19

后续已用 Intel Endurance Gaming 替换本文排查的旧算法，实现与验证结果见 [Intel 智能功耗接入](intel-endurance-integration.md)。

## 结论与范围

当前实现存在可以离线复现的决策缺陷，能够解释“帧率低却不给功耗”和“功耗反复变化”的现象。首要问题在采样有效性、升降功耗规则及错误上限的保留策略。

本次没有切换智能模式、修改用户设置或部署新算法。尚未取得用户发生异常时的游戏内连续记录，因此以下复现证明的是实现缺陷，不能直接认定某一个缺陷就是某款游戏的实际原因。

用户补充：主要在《鸣潮》中出现；手动给功耗正常，智能模式容易出现 GPU 频率与功耗偏低、低帧率及卡顿。补查时没有发现运行中的鸣潮游戏进程，未取得当场 GPU 频率与智能上限的对照记录。代码中的智能模式直接调节的是功耗上限与独立保存的 CPU 频率上限，没有直接调节 GPU 频率；GPU 低频可能是功耗预算不足后的表现，尚不能当作已经证实的根因。

## 现在怎么工作

1. Python 后台约每秒循环一次（另加采样、风扇、OSD 等操作耗时）。智能算法最短每 2 秒调整一次，通常增减 1–2 W。
2. 通过前台进程判断游戏，读取 PresentMon 的游戏自身帧率和芯片实际耗电；多条交换链中选择呈现帧率最高的一条。
3. 帧率和耗电先做权重 0.5 的平滑。只有实际耗电达到“当前上限减 1.5 W”，才认为需要增加功耗。
4. 帧率低于目标的 95% 时，若认为功耗用满就加功耗，否则反而减功耗。高于目标的 107% 时减功耗。
5. 累计加了至少 2 W 后，若下一次评估中平滑帧率没有提高 3%，立即退回原功耗，将其作为上限保留 60 秒。
6. 没有游戏时采用 12 W（受上下限约束）。目标为 0 时使用“不限帧率”的试探规则，并没有自动识别目标帧率。
7. 算法给出持续上限 PL1；短时上限 PL2 = PL1 + 短时加成。底层写入后回读校验。CPU 频率上限单独写入 Windows 电源方案，不随智能功耗自动优化。

主要位置：`plugin/claw_power.py:482`（算法）、`:766`（输入采样）、`:744`（写入校验）；`native/ClawPower.cs:1078`（帧率采集）；`frontend/library-native/ClawLibrary/Stage/WallStage.Perf.cs:310`（目标文案）。

## 已确认的问题

### 1. 采集失败被当成低帧率或低负载

`_smart_tick()` 在游戏存在、但没有交换链数据时，将帧率传成 `0.0`。`framesError` 只保存到状态，没有阻止算法决策。原生轮询失败也可能直接返回空列表；刚开始跟踪进程时同样没有样本。

因此无法区分“采集出错”“刚开始采集”“游戏静止画面”。在实际耗电偏低时，采集失败会持续触发降功耗。

离线用原始 `_smart_tick()` 注入采集错误、空交换链和 6 W 实际耗电，50 秒内上限从 35 W 降到 8 W。整个回放没有硬件写入路径。

### 2. 过早判定加功耗无效，随后限制一分钟

原生查询设置为 1000 ms 平均窗口、1000 ms 偏移，后台又做平滑；升功耗后的下一次评估可能还包含升功耗前的帧率。算法没有等待采样窗口更新、确认场景稳定或验证样本时间。

离线设定真实帧率随功耗提高，但帧率数据延迟 2 秒：16 W / 40 FPS → 第 2 秒升到 18 W → 第 4 秒误判无收益并退回 16 W → 第 5 秒才看到 45 FPS。此时 16 W 上限已经锁定，持续到第 64 秒。

这证明延迟会触发错误上限；2 秒是回放模型参数，不是本次对用户游戏采集得到的实测延迟。[Intel API 的查询参数定义](https://github.com/GameTechDev/PresentMon/blob/main/IntelPresentMon/PresentMonAPI2/PresentMonAPI.h)包含窗口长度和指标偏移。

### 3. “没吃满功耗”直接等于“加功耗没用”

算法只用芯片实际耗电与上限的差值判断瓶颈。虽然采集到了 GPU Busy 和 CPU Busy，智能决策没有使用这些信号。CPU 频率限制、游戏负载变化、采样时差等情况都没有得到单独处理。

离线构造“实际耗电为上限的 80%，性能仍随上限增加”的负载，即使始终低于 90 FPS 目标，算法仍会下降并在 8–10 W 循环。这个模型用于验证规则的反例，不代表用户游戏的真实功耗曲线。

结合用户当前保存的目标 0，补充回放了相同负载的“不限帧率”分支，同样降至 8–10 W 循环；最后一步给出的原因是“不限帧率：按实际耗电降低”。这说明该缺陷不只存在于指定帧率目标的分支。目标 60 的同一模型则在约 31 W 达标后保持，不能将所有目标设置概括为必然降至下限。

GPU Busy 可辅助分析渲染耗时与 CPU/GPU 等待关系，但也不能单凭一个指标决定升降功耗，参见 [Intel 对 GPU Busy 的解释](https://game.intel.com/stories/intel-arc-graphics-dx11-intel-presentmon-beta/)。

### 4. 游戏和会话识别不可靠

- 目前基本等于“前台程序不在排除名单中，就当游戏”，检查时已实际把 ChatGPT 识别为候选游戏。
- 前台程序被排除时，只要上次游戏仍在运行就沿用它；实际行为并不限于注释中所说的 Steam 覆盖层。
- 算法用 exe 文件名识别会话，没有使用 PID 区分同名进程重启。
- 修改目标帧率不会清除旧上限；离线已验证修改为 120 FPS 后仍保留旧的 16 W 上限。切换供电、同一游戏场景变化及离开再回到智能模式也没有明确的历史重置策略。

### 5. 页面文案和状态反馈不足

- “目标帧率：自动”实际是“不限帧率”，容易让用户误以为会自动选取屏幕刷新率或游戏限帧值。
- 智能与手动模式保存的 CPU 频率上限不同。目前从手动切智能会从 3.0 GHz 改为 2.75 GHz；这可能影响 CPU 受限游戏，不能把所有掉帧归因于功耗数值。
- 页面没有展示后台已经生成的调节原因、采样错误和错误上限剩余时间，用户无法理解为何不再加功耗。

## 建议修改顺序

1. **先修输入可信度**：区分有效样本、暂缺、采集失败和游戏失焦；采集异常时停止依据无效帧率降功耗，使用有明确边界的保底策略；按 PID 和有效渲染会话识别游戏。
2. **再改决策规则**：有效样本确认持续掉帧后较快增加功耗，持续有余量后较慢降低功耗；对齐功耗与帧率的采样窗口，连续多个稳定窗口后再判断增加功耗是否有效，避免一次判断限制一分钟。
3. **清理过期判断**：游戏 PID、目标、模式、电源或明显场景变化时使旧的试探结果失效；结合 CPU/GPU 渲染信号与 CPU 频率上限解释瓶颈。
4. **补齐界面反馈和验证**：明确“不限帧率”含义，展示当前上限、实际消耗、决策原因和采样状态；加入延迟、采集失败、场景切换、进程重启和切换电源的测试，再用具体游戏记录验证稳定性与能耗。

不建议仅增大步长或提高默认功耗，这会保留错误判断，还可能放大功耗波动。
